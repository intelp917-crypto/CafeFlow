# گزارش تست بار ۱۵۰ کاربر — CafeFlow / SQLite

تاریخ: ۲۰۲۶-۱۱-۲۱ · ایمیج‌ها: `cafeflow/api:0.1.0` و `cafeflow/web:0.1.0`
میزبان: Windows + Docker Desktop (WSL2) · Intel Core i5-13420H (۸ هسته، ۱۲ رشته) · Node 24.22 · Docker 29.9.3
استک: همان ایمیج‌های تولیدی، اما **ایزوله**: پروژهٔ `cafeflow-loadtest`، volume جدا، پورت loopback `18080`، بدون دادهٔ کافه.
هیچ preview یا بازبینی بصری انجام نشد.

## روش

- **۱۵۰ virtual user** به‌صورت closed-loop؛ هر کاربر یک درخواست در پرواز دارد.
- **۸۰٪ خواندن / ۲۰٪ نوشتن** در سطح درخواست:
  - منو ۳۵٪، وضعیت سفارش ۲۵٪، لیست سفارش‌های فعال ۲۰٪، صف آماده‌سازی ۱۰٪، داشبورد ۱۰٪.
  - نوشتن: ساخت سفارش کارکنان با نشست مدیر.
- هر نوشتن **create → cancel** است تا صف سفارش‌های فعال و آماده‌سازی مثل یک کافهٔ در حال کار بسته شود؛ بدون این کار، صف در دقیقه‌ها به هزاران ردیف می‌رسید و نتیجه مصنوعی می‌شد.
- نوشتن عمومی مشتری عمداً استفاده نشد، چون سقف `40 سفارش / ۱۰ دقیقه / IP` دارد و DB را از دید پنهان می‌کند؛ این سقف جدا اندازه‌گیری شد.
- خواندن منو با کوکی `cafe_device` انجام شد. توجه: خود GET منو یک `UPDATE customer_devices.last_seen_at` دارد، پس سهم نوشتن واقعی DB از ۲۰٪ بیشتر است.
- RPS جدول «بار منطقی» است (۸۰/۲۰). هر نوشتن یک درخواست cancel اضافه هم دارد که جزو ۲۰٪ شمرده نشده؛ ستون HTTP RPS آن را شامل می‌شود.

سه سناریو:

| سناریو | فاصلهٔ فکر | مدت |
|---|---:|---:|
| واقعی | ۱۵ ثانیه (polling وضعیت) | ۱۲۰ ثانیه |
| فشرده | ۱ ثانیه | ۶۰ ثانیه |
| اشباع | ۰ | ۳۰ ثانیه |

اندازه‌گیری event loop و CPU با preload سمت سرور (`monitorEventLoopDelay`) و لاگ هر ثانیه انجام شد. p95/p99 کلاینت روی همهٔ درخواست‌ها است. رزولوشن histogram حدود ۲۰ms است، بنابراین p95 حدود ۲۰ms یعنی «تأخیر قابل‌اندازه‌گیری ندارد».

## سقف مستقل از SQLite: ۴۰ سفارش در ۱۰ دقیقه

probe عمومی از یک IP:

```
201: 40
429: 5
```

دقیقاً ۴۰ سفارش موفق و بعد `RATE_LIMITED`. این محدودیت در `PublicService.ipOrderLimiter` است، نه SQLite. در یک کافه که همهٔ مشتری‌ها از NAT یک IP می‌آیند، این سقف قبل از دیتابیس مانع می‌شود. برای ۱۵۰ مشتری در ۱۰ دقیقه، سقف فعلی ۴ سفارش در دقیقه است.

## SQLite کجا کم می‌آورد؟

### ۱) در ۱۵۰ کاربر واقعی، نه
با polling هر ۱۵ ثانیه (۹.۹۳ RPS) p95 برابر ۸ms و p99 برابر ۱۳.۷ms بود؛ صفر خطا و صفر busy. این بار برای این استک کاملاً راحت است.

### ۲) در ۱۵۰ کاربر با فعالیت یک‌ثانیه‌ای، هم نه
۱۴۸.۶۷ RPS، p95 ۱۴ms، p99 ۲۵ms، CPU ۲۷٪. حتی نوشتن create+cancel با ۲۴ms p95 انجام شد. SQLite در این محدوده گلوگاه نیست.

### ۳) در اشباع، بله — اما نه با `SQLITE_BUSY`
در ۲۵۴ RPS منطقی (حدود ۳۰۵ RPS HTTP) و CPU ۹۸٪، p95 به ۱.۱ ثانیه رسید؛ خطا و busy صفر بود. گلوگاه **تک‌هسته‌ای بودن Node و اجرای همگام کوئری‌ها** است، نه قفل نویسنده. SQLite فقط به‌صورت غیرمستقیم سهم دارد: کوئری‌های همگام، event loop را اشغال می‌کنند و صف می‌سازند.

### ۴) `SQLITE_BUSY` در این معماری دیده نمی‌شود
استک فقط یک اتصال `better-sqlite3` در یک پروسه دارد. نوشتن‌ها روی همان event loop سریال می‌شوند؛ بنابراین busy_timeout عملاً تست نشد. این تست **ثابت نمی‌کند** دو نمونهٔ API روی یک فایل امن‌اند. اگر HA یا دو کانتینر API بخواهی، باید تست چندپروسه‌ای جدا انجام شود.

### ۵) یک «خواندن» که نوشتن است
`GET /public/menu` برای هر دستگاه شناخته‌شده `last_seen_at` را UPDATE می‌کند. در سناریوی فشرده ۲٬۵۱۱ درخواست منو یعنی حدود ۴۲ UPDATE/s اضافه، جدا از ۲۹ سفارش/s. این باعث می‌شود نسبت واقعی نوشتن DB بیشتر از ۲۰٪ باشد و اولین بهینه‌سازی کم‌هزینه باشد: throttle کردن `last_seen_at` (مثلاً هر ۵ دقیقه).

### ۶) سقف محصولی قبل از سقف DB
۴۰ سفارش/۱۰دقیقه/IP برای یک کافهٔ ۱۵۰ نفری کافی نیست. این باید قبل از مهاجرت PostgreSQL اصلاح شود، وگرنه دیتابیس جدید هم پشت ۴۲۹ پنهان می‌ماند.

## جمع‌بندی

- **برای ۱۵۰ کاربر هم‌زمان با رفتار واقعی (polling 15s): SQLite فعلی کافی است.**
- **برای ۱۵۰ کاربر با فعالیت یک‌ثانیه‌ای: هم کافی است؛ p95 = ۱۴ms.**
- **سقف این ماشین/معماری حدود ۲۵۰ RPS است**؛ از آنجا به بعد p95 > ۱ ثانیه می‌شود. این سقف بیشتر مربوط به یک هستهٔ Node و کوئری‌های همگام است تا قفل SQLite.
- **مهاجرت به PostgreSQL با عدد ۱۵۰ کاربر توجیه نمی‌شود.** توجیه‌های واقعی: چند نمونه API/HA، چند شعبه، نیاز به چند هسته برای کوئری، یا عبور پایدار از حدود ۱۵۰–۲۵۰ RPS.
- قبل از هر مهاجرت: سقف ۴۰ سفارش/IP اصلاح شود و `touchDevice` throttle شود. بعد با همان تست، اثر آن اندازه‌گیری شود.

## محدودیت‌ها

- فقط یک میزبان Docker Desktop؛ نتیجه روی لینوکس تولیدی می‌تواند بهتر باشد.
- فقط API/nginx؛ بار دارایی‌های استاتیک و WebSocket بازی‌ها در این عدد نیست.
- نوشتن‌ها create→cancel هستند، نه چرخهٔ کامل پرداخت/چاپ. این برای steady-state و بار DB کافی است، اما مسیر پول را جایگزین نمی‌کند.
- تست چند نمونه API، هم‌زمانی backup و قطع برق انجام نشد.
- p95 کلاینت شامل صف شبکه/nginx است؛ event loop سرور جدا اندازه‌گیری شده است.
- `monitorEventLoopDelay` رزولوشن ۲۰ms دارد؛ اعداد پایین‌تر از ۲۰ms را قطعی تفسیر نکن.

```bash
# 1) استک ایزوله
LOADTEST_ADMIN_PASSWORD='...' LOADTEST_WEB_PORT=18080 \
  docker compose -f infra/docker/compose.loadtest.yml up -d api web

# 2) توکن QR را از volume موقت بخوان
docker compose -f infra/docker/compose.loadtest.yml exec -T api \
  node -e "const D=require('better-sqlite3');const db=new D('/app/data/cafeflow.db');console.log(db.prepare('SELECT qr_token FROM qr_codes WHERE is_active=1 LIMIT 1').get().qr_token)"

# 3) سناریو
LOADTEST_ADMIN_PASSWORD='...' LOADTEST_QR_TOKEN='...' \
LOADTEST_VUS=150 LOADTEST_THINK_MS=1000 LOADTEST_WARMUP_MS=10000 \
LOADTEST_DURATION_MS=60000 LOADTEST_LABEL=stress \
node scripts/loadtest/run.mjs

# 4) تحلیل event loop و SQLITE_BUSY
docker logs "$(docker compose -f infra/docker/compose.loadtest.yml ps -q api)" \
  > test-artifacts/loadtest-stress-api.log
node scripts/loadtest/analyze.mjs \
  test-artifacts/loadtest-stress.json test-artifacts/loadtest-stress-api.log
```
