# ۱۰. معماری چاپ

> وضعیت: **پیاده‌شده در فاز ۵ برای رسید فروش.** صف در `print_jobs`، متن رسید در API ساخته می‌شود و پل
> نمونه `scripts/print-bridge.mjs` آن را به فایل متنی می‌نویسد. چاپ مستقیم ESC/POS و بلیت آشپزخانه
> پیاده نشده است (فاز ۷).

## محدودیت واقعی مرورگر

مرورگر **نمی‌تواند** بدون تعامل کاربر به چاپگر حرارتی محلی (USB/شبکه) داده بفرستد:

- `window.print()` پنجره دیالوگ سیستم را باز می‌کند و برای چاپ خودکار سفارش آشپزخانه مناسب نیست.
- WebUSB/WebSerial فقط با انتخاب صریح دستگاه توسط کاربر و در عمل محدود به HTTPS و مرورگرهای خاص است.
- هیچ API استانداردی برای ارسال خام ESC/POS به چاپگر شبکه وجود ندارد.

بنابراین چاپ از طریق **پل محلی** انجام می‌شود، نه از مرورگر.

## معماری

```
[سفارش ثبت شد]
      │
      ▼
print_jobs (queued, job_key یکتا)
      │  long-poll با توکن پل
      ▼
[Print Bridge Agent]  ← اجرا روی رایانه‌ای در شبکه رستوران
      │  رندر ESC/POS فارسی (bitmap برای متون فارسی)
      ▼
چاپگر حرارتی (TCP 9100 یا USB)
      │
      ▼
print_jobs.status = printed | failed (+attempts, last_error)
```

### `printers`

| ستون | معنا |
|---|---|
| `kind` | `receipt`, `kitchen`, `barista`, `other` |
| `department_id` | تطبیق با `order_items.department_id` |
| `connection` | `tcp`, `usb`, `bridge` |
| `address` | مثل `192.168.1.50:9100` یا مسیر دستگاه |

### `print_jobs`

- `job_key` یکتا (`order:{id}:{department}:{itemId}`) → همان سفارش دو بار چاپ نمی‌شود.
- `status`: `queued → sent → printed` یا `failed` با `attempts` و `last_error`.
- چاپ مجدد فقط با مجوز و با `job_key` جدید (برای ردگیری) و ثبت در `audit_logs`.

## قواعد مسیریابی

- هر آیتم فقط به چاپگر دپارتمان خودش می‌رود (قهوه → باریستا، غذا → آشپزخانه، سایر نوشیدنی → بار).
- رسید مشتری فقط در زمان تسویه به چاپگر صندوق می‌رود، نه در زمان ثبت سفارش.
- اگر چاپگری تنظیم نشده باشد، کار در صف `failed` ثبت می‌شود و **سفارش متوقف نمی‌شود**.

## فارسی و ESC/POS

- چاپگرهای حرارتی معمولاً کدپیج فارسی ندارند؛ پل چاپ متن فارسی را به **تصویر بیت‌مپ تک‌رنگ** تبدیل و با فرمان `GS v 0` چاپ می‌کند (قابل اعتمادترین روش).
- برای چاپگرهای دارای کدپیج فارسی (`CP864`/`Iran System`)، حالت متن خام قابل انتخاب است.
- قالب رسید: نام مجموعه، شماره میز/سفارش، اقلام با تعداد و مبلغ، جمع، تخفیف، مالیات، تاریخ جلالی، تشکر پایانی.

## آنچه در فاز ۵ واقعاً پیاده شد

- `POST /orders/:id/receipt` متن رسید را می‌سازد و در `print_jobs` با `job_key = receipt:{orderId}:{paidTotal}`
  ذخیره می‌کند (کلید یکتا = ضد چاپ تکراری؛ پس از تغییر مبلغ، رسید جدید مجاز است).
- `GET /print/jobs?status=queued` صف را با متن رسید برمی‌گرداند؛ `POST /print/jobs/:id/printed` و
  `/failed` وضعیت، `attempts`، `printed_at` و `last_error` را ثبت می‌کنند.
- `scripts/print-bridge.mjs` با یک حساب کارمند دارای `orders.read` وارد می‌شود، هر کار صف را در
  `print-output/<code>-<id>.txt` می‌نویسد و نتیجه را برمی‌گرداند. خروجی متنی را می‌توان به هر درایور
  (CUPS/lpr، آداپتور سریال یا مبدل ESC/POS) داد؛ خود اسکریپت هیچ کد سخت‌افزاری ندارد.
- صفحه `/admin/print` صف را نشان می‌دهد و اجازه تأیید دستی چاپ/شکست را می‌دهد (برای نصب بدون پل).
- قالب رسید: نام مجموعه، «رسید فروش»، کد سفارش، میز، تاریخ جلالی، اقلام با گزینه/افزودنی/یادداشت،
  جمع اقلام، تخفیف، حق سرویس، مالیات، مبلغ کل، پرداخت‌شده و روش‌های پرداخت.

**اجرای پل:**

```bash
PRINT_BRIDGE_USERNAME=cashier PRINT_BRIDGE_PASSWORD=... node scripts/print-bridge.mjs
# اختیاری: API_BASE، PRINT_OUTPUT_DIR، PRINT_INTERVAL_MS
```

## امنیت

- پل با **نشست کارمند** (کوکی `HttpOnly`، همان ورود عادی) احراز می‌شود و فقط مجوزهای همان حساب را دارد؛
  توکن جداگانه یا کلید مشترک وجود ندارد. برای همین از حسابی با حداقل مجوز (`orders.read`) استفاده کنید.
- رمز پل در محیط همان ماشین تنظیم می‌شود و در مخزن قرار نمی‌گیرد؛ هیچ رمزی در بسته کلاینت نیست.
- API هرگز به پرینتر وصل نمی‌شود؛ فقط صف + متن. دسترسی پل به شبکه محلی محدود می‌شود.
