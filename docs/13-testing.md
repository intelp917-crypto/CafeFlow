## وضعیت مهاجرت Rust (موج ۱، ۳، ۴، ۵ و ۶)

- `cafeflow-domain`: پول ریالی، جلالی، وضعیت سفارش و ماژول‌ها با آزمون برابری.
- `cafeflow-db`: مهاجرت‌های SQLite/PostgreSQL، `schema_migrations` سازگار با نصب فعلی،
  scrypt سازگار با هش‌های Node، seed نقش/مجوز/مدیر، TOTP و کدهای پشتیبان.
- `cafeflow-api`: health، login/logout/me، نشست‌ها، تغییر گذرواژه، MFA، هدرهای امنیتی،
  request-id، SPA fallback و ۴۰۴ واقعی برای media؛ آزمون‌های `auth_flow` و `totp`.
- موج ۳: `GET /public/menu`، `POST /public/orders` با محاسبهٔ قیمت سمت سرور و idempotency،
  `GET /public/orders/:code` با توکن وضعیت، و `GET /dashboard/overview` برای داشبورد کارکنان؛
  آزمون `public_flow` شامل replay، رد گزینهٔ نامعتبر و دسترسی محافظت‌شدهٔ داشبورد.
- موج ۴: `GET /orders` با فیلتر/صفحه‌بندی، `GET /orders/:id` با اقلام/گزینه‌ها/تاریخچه/صورت‌حساب،
  و `POST /orders/:id/transition` با همان ماشین وضعیت، مجوز `orders.cancel`، دلیل لغو، لغو صف
  آماده‌سازی، آزادسازی میز و audit؛ آزمون `staff_can_list_inspect_and_transition_orders`.
- موج ۵: `GET /tables`، `POST /orders` برای سفارش دستی با قیمت‌گذاری سمت سرور،
  `POST /orders/:id/items`، `PATCH /orders/:id/items/:itemId` با بازمحاسبهٔ کل، و
  `POST /orders/:id/{tickets,receipt}` با jobKey یکتا؛ آزمون
  `staff_can_create_edit_and_print_an_order`.
- موج ۶: `GET /prep/queue` با فیلتر دپارتمان و آیتم‌های پایان‌یافته، و
  `POST /prep/:id/transition` با همان ماشین وضعیت آماده‌سازی. تغییر هر آیتم، وضعیت قلم و
  سفارش را از کوتاه‌ترین مسیر مجاز پیش می‌برد (`confirmed → preparing → partially_ready → ready`)،
  رویداد `order.status_auto` و اعلان `order.ready` می‌سازد و پایان کار را در صف مخفی می‌کند؛
  آزمون `prep_queue_advances_the_order_along_legal_paths`.
- seed دمو اکنون کاتالوگ قابل استفاده می‌سازد: ۲ دسته، ۵ محصول، ۳ میز با QR و گزینه/افزودنی؛
  آزمون `demo_menu_seed_creates_a_ready_to_order_catalog`.
- `cafeflow-games`: فقط registry اتاق در این موج؛ موتورهای ۳۸ بازی هنوز منتقل نشده‌اند.
- آزمون دستی انجام‌شده: SQLite تازه، PostgreSQL تازه (`postgres:17-alpine`)، کپی ۵۲۶ ردیف
  از snapshot موجود، ورود مدیر و `/auth/me` روی هر دو، SPA و deep link روی باینری؛ در موج ۴
  فهرست/جزئیات/انتقال سفارش روی PostgreSQL و مرورگر واقعی هم تأیید شد. در موج ۶ صف
  آماده‌سازی روی PostgreSQL تازه و در مرورگر واقعی (شروع/آماده‌شدن دو دپارتمان) تأیید شد.
- **هنوز منتقل نشده:** پرداخت/صندوق، کاتالوگ مدیریت، گزارش، درخواست گارسون
  و کارت‌خوان، صف چاپ و بازی‌ها. تا سبز شدن آزمون برابری، cutover انجام نمی‌شود.

## E2E مرورگر (فاز ۷)

```bash
npx playwright install msedge   # فقط یک‌بار اگر Edge نصب نیست
npm run test:e2e
```

- پیکربندی: `playwright.config.ts`؛ آزمون‌ها در `apps/web/e2e/`؛ مرورگر: Edge نصب‌شده (`channel: 'msedge'`).
- هر اجرا سرورهای ایزولهٔ خودش را بالا می‌آورد (`reuseExistingServer: false`) تا هرگز به dev server یا دیتابیس توسعه‌دهنده وصل نشود.
- ۱۸ سناریو در ۶ فایل: مسیر کامل پول/رسید، منوی مشتری، ورود و داشبورد، رزروها، MFA، PWA و هدرها،
  دو گوشی روی یک میز، پوشش همهٔ مسیرهای عمومی و ۲۴ مسیر ادمین با assert عنوان اختصاصی هر صفحه،
  ناوبری چهار نقش، CRUD کاتالوگ و انبار، بازکردن رزرو، و بررسی سرریز افقی HomePage و مسیرهای کلیدی در ۳۶۰px.
- آخرین اجرا: **۱۸ passed** با Edge واقعی، بدون preview دستی؛ در شکست، trace/screenshot خودکار Playwright.

## تست بار ۱۵۰ کاربر

روی همان ایمیج‌های تولیدی و SQLite، با ۱۵۰ virtual user و نسبت ۸۰/۲۰. جزئیات کامل، p95/p99،
`SQLITE_BUSY` و event loop در [`LOAD-TEST-REPORT.md`](LOAD-TEST-REPORT.md). نتیجهٔ کوتاه:
بار واقعی polling ۱۵ ثانیه‌ای p95 = ۸ms و صفر خطا داشت؛ در فشار ۲۵۴ RPS منطقی، CPU تک‌هسته به
۹۸٪ رسید و p95 = ۱.۱s شد، بدون `SQLITE_BUSY`.

### تأیید PWA در حالت تولیدی

```bash
npm run build
docker compose -f infra/docker/compose.yml up -d
PWA_BASE_URL=http://127.0.0.1:8080 node scripts/verify-pwa.mjs
```

- `scripts/verify-pwa.mjs` با Edge واقعی بررسی می‌کند: لینک manifest، تجزیه آن، فعال‌شدن سرویس‌ورکر و
  پاسخ‌دادن به reload در حالت آفلاین با `offline.html`.
- آخرین اجرا: **۴/۴ موفق** روی استک واقعی nginx/Docker (manifest از `/api` می‌آید و `vite preview`
  بدون پروکسی API برای این بررسی کافی نیست). سرویس‌ورکر عمداً فقط در بیلد تولیدی ثبت می‌شود.

## چرا این آزمون‌ها معنادارند

- آزمون‌های یکپارچه **برنامه واقعی Nest** را با پایگاه داده واقعی (فایل موقت مستقل برای هر فایل آزمون) بالا می‌آورند؛ همان guardها و همان SQL اجرا می‌شود. هیچ ماک‌ای برای لایه امنیت وجود ندارد.
- حالت `fileParallelism: false` تضمین می‌کند فایل‌های SQLite هم‌زمان باز/بسته نشوند (ویندوز قفل فایل را سخت‌گیرانه‌تر مدیریت می‌کند).
- آزمون ماژول یک ردیف واقعی `ingredients` می‌سازد و پس از خاموش‌کردن ماژول بررسی می‌کند که ردیف باقی مانده است — دقیقاً همان قاعده‌ای که در سند ۶ وعده داده شده.

## E2E (فاز ۷)

سناریوی مرجع:

1. اسکن QR میز → منو
2. انتخاب محصول و ارسال سفارش
3. اعلان گارسون → تأیید
4. باریستا/آشپزخانه آیتم‌ها را آماده می‌کنند
5. وضعیت سفارش به‌روزرسانی می‌شود
6. صندوق پرداخت را ثبت می‌کند
7. رسید چاپ می‌شود
8. میز آزاد می‌شود

موارد مرزی: دو سفارش هم‌زمان، قطع شبکه، درخواست تکراری، دسترسی غیرمجاز، ماژول خاموش، RTL و تاریخ جلالی.

گزارش کامل اجرا و محدودیت‌ها: [`TEST-REPORT.md`](TEST-REPORT.md).

## قواعد

- هر باگ امنیتی یا مالی **قبل از رفع** یک آزمون شکست‌خورده دارد.
- هیچ آزمونی برای «سبز شدن» تضعیف نمی‌شود؛ اگر قاعده عوض شد، آزمون با دلیل به‌روزرسانی می‌شود.
- CI در فاز ۷: `npm run build && npm test` روی هر push.
