# ۱. معماری سیستم (System Architecture)

## نمای کلی

CafeFlow یک سامانه یکپارچه مدیریت کافه و رستوران است: بک‌اند تولیدی یک باینری Rust/Axum است
که API، WebSocket بازی‌ها، فایل‌های آپلودی و SPA ساخته‌شده را روی یک پورت سرو می‌کند.

```
rust/crates/api Rust/Axum — REST API، احراز هویت، RBAC، صف‌ها، چاپ، WebSocket بازی‌ها
rust/crates/games اتاق‌ها + موتور قواعد ۳۸ بازی داخل Boa
rust/crates/db  مهاجرت‌ها و SQLite/PostgreSQL
rust/crates/domain پول، جلالی، وضعیت سفارش، نرمال‌سازی فارسی
apps/api        NestJS 11 — مرجع تاریخی و آزمون برابری (در تولید اجرا نمی‌شود)
apps/web        React 19 + Vite + Tailwind 4 — مشتری، کارکنان، مدیریت
packages/shared منطق دامنه مشترک (ماشین وضعیت، مجوزها، پول، جلالی، نرمال‌سازی فارسی)
packages/ui     سیستم طراحی RTL-first
infra/docker    Dockerfile.rust و compose.rust.yml — یک image/یک container
docs            مستندات فنی
```

## لایه‌ها

```
HTTP/WS →  Router (Axum) + احراز نشست/مجوز/ماژول
        →  Handler (اعتبارسنجی ورودی، پاسخ JSON)
        →  ماژول دامنه (قواعد کسب‌وکار، تراکنش)
        →  SQLx با کوئری پارامتری
        →  SQLite (WAL) یا PostgreSQL
```

- **Handler** فقط ورودی را اعتبارسنجی می‌کند و خروجی JSON می‌دهد؛ قاعده کسب‌وکار در آن نیست.
- **ماژول دامنه** مرجع قواعد است: محاسبه مبلغ، انتقال وضعیت سفارش، بررسی تخفیف، ثبت حسابرسی.
- **SQL** فقط در لایهٔ داده/هندلرهای همان دامنه است و همهٔ کوئری‌ها پارامتری‌اند.
- **Shared** منطق خالص و قابل‌آزمون (ماشین وضعیت سفارش، محاسبات ریال، جلالی، جست‌وجوی فارسی) را نگه می‌دارد تا API و UI از هم جدا نشوند.

## Guardهای سراسری (به ترتیب)

1. **نشست** — کوکی `HttpOnly` خوانده می‌شود، هش توکن در `sessions` جست‌وجو می‌شود و کاربر/نقش/مجوز/ماژول در state درخواست قرار می‌گیرد. مسیرها خصوصی‌اند؛ فقط handlerهای عمومی استثنا هستند.
2. **مجوز** — همهٔ مجوزها از پایگاه داده بررسی می‌شوند (نه از کلاینت).
3. **ماژول** — handlerهای اختیاری (`games`، گزارش‌ها و…) با خاموش بودن ماژول ۴۰۳ فارسی برمی‌گردانند؛ سوکت بازی هم پیش از handshake با ۵۰۳ بسته می‌شود.

## ارتباط بلادرنگ (فاز ۳)

طراحی بر این اصل استوار است که **WebSocket فقط «تکان» است، نه منبع حقیقت**:

- رویدادها از طریق سوکت اطلاع می‌دهند «چیزی تغییر کرد»؛ کلاینت داده را با REST دوباره می‌خواند.
- هر رویداد `id` یکتا دارد تا تکرار حذف شود.
- در قطع اتصال، پلینگ REST جایگزین می‌شود و پس از اتصال مجدد `GET /rt/state` وضعیت را همگام می‌کند.
- اتاق‌ها: `floor:{id}`، `dept:{id}`، `role:{key}`، `user:{id}`؛ عضویت با همان مجوزهای REST تعیین می‌شود.

## صف‌ها و کارهای پس‌زمینه (فاز ۴–۵)

بدون Redis: جدول‌های `notification_outbox` و `print_jobs` صف پایدارند. یک worker در همان پردازش API با
`UPDATE ... WHERE status='queued'` ردیف را برمی‌دارد (ادعای اتمی) و پس از تلاش، `attempts`/`last_error`
را ثبت می‌کند. شکست ارسال هرگز سفارش را متوقف نمی‌کند.

## تصمیم‌های معماری کلیدی

| تصمیم | دلیل |
|---|---|
| SQLite با WAL به‌جای PostgreSQL در توسعه | محیط فعلی Docker/PostgreSQL ندارد؛ اسکیما به‌صورت قابل‌انتقال نوشته شده (UUID، عدد صحیح ریال، FK، ایندکس یکتا جزئی) |
| کلیدهای UUID متنی | تولید سمت برنامه، سازگار با PostgreSQL، مناسب همگام‌سازی آینده |
| مبلغ به عدد صحیح ریال | حذف خطای اعشاری؛ محاسبه معتبر فقط سمت سرور |
| `emitDecoratorMetadata: false` | تزریق صریح `@Inject(TOKEN)` تا کد در tsc، tsx و Vitest یکسان اجرا شود |
| کوکی نشست `HttpOnly` + SameSite=Lax | بدون نگه‌داشتن توکن در JavaScript؛ همان‌مبدا بودن با پروکسی Vite |
| ماژول‌های اختیاری از طریق رجیستری + Guard | هسته هرگز به ماژول اختیاری وابسته نمی‌شود |

## مرزهای ماژول

`packages/shared/src/modules.ts` تنها منبع حقیقت است: کلید، نام فارسی، پیش‌فرض، قابلیت پیکربندی،
وابستگی و فاز. API و UI هر دو از همین فهرست می‌خوانند.
