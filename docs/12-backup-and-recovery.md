# ۱۲. پشتیبان‌گیری و بازیابی

## چه چیزی باید پشتیبان گرفته شود؟

| مسیر | چرا |
|---|---|
| `$CAFEFLOW_DATA_DIR/cafeflow.db` (پیش‌فرض توسعه: `data/cafeflow.db`) | تمام داده کسب‌وکار |
| `$CAFEFLOW_DATA_DIR/cafeflow.db-wal` و `-shm` | تراکنش‌های تأییدنشده در WAL |
| `$CAFEFLOW_DATA_DIR/print-output/` | رسیدهای پل چاپ (اختیاری؛ از صف چاپ قابل بازتولید است) |
| `.env` (جدا، رمزنگاری‌شده) | تنظیمات و کلیدها |

> لوگوی آپلودشده به‌صورت data URL داخل همان پایگاه داده ذخیره می‌شود؛ پوشهٔ `uploads/` وجود ندارد.

## روش صحیح در حالت WAL

کپی خام فایل `.db` وقتی سرور در حال نوشتن است ممکن است ناسازگار باشد. یکی از دو روش:

```bash
# ۱) پشتیبان آنلاین سازگار (توصیه‌شده، نیازی به توقف سرور نیست)
sqlite3 data/cafeflow.db ".backup 'backups/cafeflow-$(date +%F).db'"

# ۲) توقف کوتاه سرور
systemctl stop cafeflow-api
cp data/cafeflow.db* backups/...
systemctl start cafeflow-api
```

در ویندوز بدون `sqlite3` CLI می‌توان از `better-sqlite3` استفاده کرد:

```js
const db = require('better-sqlite3')('data/cafeflow.db');
db.backup(`backups/cafeflow-${new Date().toISOString().slice(0,10)}.db`);
```

## زمان‌بندی پیشنهادی

- **روزانه** (نیمه‌شب تهران): پشتیبان کامل + نگه‌داری ۱۴ روز.
- **هفتگی**: نگه‌داری ۸ هفته در محل جدا.
- **ماهانه**: نگه‌داری ۱۲ ماه، خارج از سرور (S3/دیسک خارجی) و ترجیحاً رمزنگاری‌شده (`age`/`gpg`).

Docker Compose یک سرویس `backup` دارد که همین اسکریپت `scripts/backup.mjs` را بلافاصله پس از بالا آمدن
API و سپس هر ۲۴ ساعت اجرا می‌کند (`BACKUP_KEEP`، پیش‌فرض ۱۴). این سرویس از همان تصویر API استفاده
می‌کند، پس به نصب یا شبکهٔ زمان اجرا وابسته نیست؛ چون volume پشتیبان روت‌مالک است، تنها همین سرویس با
`user: "0:0"` اجرا می‌شود و mount داده‌اش `:ro` نیست (SQLite برای WAL به `-shm` قابل‌نوشتن نیاز دارد).
روی استک واقعی آزموده شد: فایل ساخته شد و `integrity_check=ok` داد.

## بازیابی

```bash
systemctl stop cafeflow-api
cp data/cafeflow.db data/cafeflow.db.bak-$(date +%s)   # نگه‌داشتن وضعیت فعلی
rm -f data/cafeflow.db-wal data/cafeflow.db-shm
cp backups/cafeflow-2026-11-18.db data/cafeflow.db
systemctl start cafeflow-api
curl -s localhost:3000/api/v1/health
```

پس از بازیابی:

1. `npm run db:migrate` را اجرا کنید (اگر نسخه پشتیبان قدیمی‌تر است، مهاجرت‌های جدید اعمال می‌شوند).
2. با حساب مدیر وارد شوید و داشبورد را بررسی کنید.
3. در `audit_logs` رویدادهای پس از زمان پشتیبان وجود ندارند؛ این طبیعی است و باید به کاربران اطلاع داده شود.

## آزمون بازیابی

هر ماه یک بار پشتیبان را روی محیط آزمایشی بازیابی و این موارد را بررسی کنید:

- ورود موفق مدیر
- تعداد محصولات/میزها/کارکنان مطابق انتظار
- باز شدن گزارش رویدادها
- اجرای `npm test` روی همان نسخه کد

## نکات

- پشتیبان بدون آزمون بازیابی ارزش عملیاتی ندارد.
- دسترسی به پوشه پشتیبان باید محدود باشد (حاوی داده مشتریان و تراکنش‌ها است).
- پیش از مهاجرت بزرگ یا ارتقای نسخه، همیشه پشتیبان دستی بگیرید.
